Journey API

Give the planner two locations and a departure time. It returns catchable bus options with the walk, platform wait, ride and arrival at your destination.

GET /journeys

Enter latitude,longitude or a GTFS stop ID. The starting pins are near Rohini Sector 22 and Azadpur. This example uses October GPS replay.

Read a route

    

      
Locations and departure
from and to also accept stop names. Use /stops to resolve names with multiple platforms. Omit depart for current service or specify an ISO 8601 timestamp. Times without an offset use India Standard Time.

      
Alternatives
Each journeys[] entry gives destination arrival and total seconds. Walk, wait and ride add up to that total. max_transfers=0 restricts the search to direct services. The default permits one change. Use compare_hour=13 to check 13:00 on the same date.

      
Walk and wait
Access, transfer and egress walks each have a seconds field, including zero at the platform. Wait runs from reaching the platform until the predicted boarding departure. A transfer wait includes the 90-second minimum change allowance once. To check a route for someone already at the platform, try a GPS-based arrival at Jag Jivan Ram Hospital. Its prediction can use a bus seen upstream whose ultimate destination is unconfirmed.

      
When the bus may still be boarding
When a live departure falls up to one minute before the rider reaches the platform, check boarding_alerts[] for a conditional_itinerary and a fallback_itinerary. Display both arrival times. The rider should choose the possible bus only if they can see it taking passengers. For a 31–60 second gap, keep the ordinary journey selected. The full judge package includes the dated 502UP replay.

      
Walking the whole way
A separate walking_alternative can appear when a mapped pedestrian path within 2 km beats the bus or the search finds no bus. It carries the walking geometry, estimated time and any warning about an unconfirmed sidewalk.

      
Stops and timing
Each bus leg has boarding and alighting platforms, route, trip, stop calls and a timing source. Each call gives arrival and departure. Where the published shape aligns, the API returns route metres and estimated average km/h from the previous served stop. A null speed means there is insufficient evidence.

      
Vehicle evidence
Use gps_age_seconds and vehicle_approaching to tell riders when a conditional bus was last located and whether it was moving toward their platform. A platform response can also include route_observation for a bus seen upstream whose timetable trip could not be identified. Show its observed stop and time separately from the next bus’s ETA.

      
Map coordinates
Leg geometry is a list of [latitude, longitude] pairs. A bus with geometry_source: ordered_stops has only a schematic line between platforms.

      
Empty responses
A valid search with no feasible path returns HTTP 200, an empty journeys array and a reason in warnings. An invalid date, unknown stop or out-of-range coordinate returns HTTP 422 with detail.

    

  

  
Timing evidence

    
Inspect feed freshness and GPS coverage. Live stop predictions, recent observed bus travel, historical GPS and the timetable can all occur in one journey. The response identifies its sources per leg and per stop call.

    
Read the pre-departure forecasts and GPS trial results in JSON or compare the journeys on screen. Each result identifies the walking assumption and which bus stops GPS could verify.
